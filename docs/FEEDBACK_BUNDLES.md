# Reading a Desktop feedback bundle

Help > Export current conversation feedback bundle saves a local `.json.gz` file. It does not upload it or choose a recipient. The user decides whether to share it with Desktop maintainers, Step Code maintainers, or another relevant provider.

Decompress the file as gzip to read the JSON (`dfsc-local-feedback-v3` for a single turn, `dfsc-local-feedback-v4` for multiple turns). With Node.js:

```sh
node -e "process.stdout.write(require('node:zlib').gunzipSync(require('node:fs').readFileSync(process.argv[1])))" feedback.json.gz
```

- Read `actual` and `expected` first. Use `context` to check the Desktop version, Step Code baseline and commit, platform, and architecture before reproducing.
- Choose the latest recorded issue, the latest saved turn, or up to 32 specific saved turns from the current branch. The history selector starts with 10 recent abnormal turns per page and also offers all turns, including turns without errors. Steering stays with its running turn; a recorded automatic turn is separate from the preceding human turn. Unfinished live output is not included. The actual session ID, picker keys and original turn numbers are not exported. `turn.startedAt`, `turn.interrupted` and recorded `turn.outcome` describe a single turn when known. In v4, `turns[].turn` is a sequential number local to the bundle; events and excerpts use it as a reference.
- In v4, `gaps` count unselected intervening turns. By default the `overview` is null and the turns contribute no evidence. An opt-in overview records aggregate outcomes and issue counts only; it does not include their contents, request IDs, individual times or event timeline. `unknown` means no authoritative turn end was recorded, not that a turn failed or succeeded. Separate turns, even with similar issues or a later completed outcome, do not prove shared cause or recovery.
- `summary` counts recorded model failures, tool issues and tools not run across the detailed turns, before the event limit. Tool issues include failures, timeouts, aborts, denials and policy blocks. `not_run` is counted separately. `notRunReasons` counts recognized runtime codes such as `invalid_arguments` without arguments or validation messages. The timeline has a 64-event single-turn limit or 128-event multiple-turn limit. It reserves the first issue, last model failure, last tool issue and last event for each detailed turn when present before sharing remaining space. `omittedEvents` is the number dropped at this limit, not the number of missing runtime records or unselected turns. A tool listed under `toolsWithOnlyFinalResult` has a terminal result but no recorded start; a tool under `toolsWithNoResult` has no terminal result. Neither implies what happened inside the tool.
- `reportedAt` is the time entered by the user. `events[].at` is the time carried by the recorded message or tool trace. These may differ; neither is the bundle creation time (`at`). Do not use manual time to infer a request match.
- Read `events` in recorded order. Tool events with the same `call` belong to one invocation within this bundle; the number is local to the report, not a request ID. A terminal trace and its matching saved tool result represent one result, not two failures. Intermediate tool output is not scanned to infer errors.
- For a model failure, check `statusCode`, `statusSource`, and `outcome`. `error_text` means the HTTP code was extracted from the error string instead of confirmed by request telemetry. `transportAttempts` is the count reported by the runtime, not a per-attempt timeline. A verified `requestId` can help the provider find the attempt, but does not guarantee log availability. A null ID means no ID was verified for that event or it could not be included.
- For a reply that completed but looks wrong, read the user's expected result and any opted-in excerpts, then try a minimal reproduction. No recorded failure is not evidence that the product worked correctly.

`summary.toolIssueGroups` keeps the count of recorded tool issue events by result and recognized reason, before timeline clipping. The same call can have multiple records; counts are not unique calls or proof of root cause. Only a fixed Step Code label for a tool requested in a linked execution trace can appear here; the label does not prove the tool existed or ran. Other or unidentified tools are grouped without a name. Multi-turn reports attribute groups to the included turn number; intervening summary-only turns have no named groups. The preview shows the most common groups, with the full breakdown in the JSON.

`summary.optionalText` distinguishes text excluded by choice, not recorded, included, or omitted at the redaction limit. Notes and opted-in detailed turns share one bounded redaction scope. At the limit, `summary.redactionLimited` is true even if excerpts were not requested. The bundle keeps structured evidence, including fixed tool issue labels, but omits notes, optional excerpts, and event identifiers. A note could echo a credential declared in context that the scanner did not reach. Review the preview before sharing: redaction is not a guarantee, particularly for secrets pasted into notes. Optional excerpts and error detail may be truncated. Saving writes the previewed JSON without re-reading live messages. Ask for the smallest additional evidence needed; do not ask for a full session or raw credentials by default.
