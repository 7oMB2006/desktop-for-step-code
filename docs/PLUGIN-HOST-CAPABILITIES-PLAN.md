## 1. 本轮要解决什么

用户反馈落到三项交付：

1. 作者不应因市场不运行 npm/pip，就误以为只能零依赖、必须手写 MCP。
2. BVR、StepAudio 及后续插件应复用同一套宿主账户授权与模型调用能力，
   不再按插件名称逐个增加宿主特例。
3. 作者应从社区市场入口找到已有的配置表单协议，不必照着 BVR 重写配置 CLI。

依赖问题主要是我们的交付规范和引导不完整，不应把踩坑归咎于作者。
SDK、模型 API 和宿主授权是不同的契约，不能用一个占位字符串混合表达。
这里的“通用 auth”指 DFSC 对宿主账户的受控授权和代发请求，
不是获取 OAuth Token 的接口，也不是另接一个第三方身份服务。

本轮仅整理、审查并提交计划 PR；不改运行时代码，不修改作者仓库、
真实账户或日用配置，不安装、调用付费模型、打包、合并或发布。

## 2. 当前事实和缺口

| 项目 | 已核实的现状 | 本计划的处理 |
| --- | --- | --- |
| 依赖安装 | 市场安装复制审核后的文件，不运行依赖安装或作者脚本 | 保留；提供正式自包含交付路径 |
| 打包产物 | 同步器不按 `dist/` 名称禁用文件；Git 跟踪、路径、锁和体积限制仍须满足 | 文档、忽略规则和真实打包样例一起验证 |
| 通用配置 | 已有 `dfsc.settings.json`、`json-file-v1` 和配置读取示例 | 提升可发现性，不再造第二套配置协议 |
| 插件更新 | 主线已有显式更新、配置保留和恢复；市场 README 仍写卸载重装 | 对齐文档与支持矩阵，不重复开发更新器 |
| 宿主账户 | BVR 桥仅有专用适配，支持受控 text/video/asr | 提取可复用的 broker，不直接公开旧 BVR 桥 |
| 凭据注入 | runtime 在 `STEPFUN_API_KEY` 未声明时尝试补入 Step 登录凭据 | 第三方 MCP 默认关闭该兜底，不靠作者 sentinel 保安全 |
| StepAudio | 声明的是 `STEP_API_KEY` 占位符，未阻止上述补入 | 先以假凭据回归覆盖，再做普通作者适配 |
| 运行隔离 | 原生 MCP 以同一 OS 用户运行，不是恶意插件沙箱 | 安装和授权界面明确披露，不能用哈希审核替代隔离 |

此前的纯假凭据测试已复现“插件子进程收到自动补入的凭据”。
没有用真实账户做泄露测试，也没有证据表明真实凭据已经外传。
Step Plan 各地区的 TTS、音色查询和复刻支持尚未由本轮验证，不能据文档猜测开放。

## 3. 首版范围和原则

首版采用“作者构建、自包含分发、用户不执行包管理器”的交付方式。
作者可以使用官方 MCP SDK、构建工具和其他合法依赖，发布物仍包含这些第三方代码，
需要保留许可证、来源和锁定信息；不能宣传成没有第三方代码或自动保证安全。

首版范围：

- 凭据隔离覆盖 Desktop 管理的插件 MCP 和手工配置的第三方 MCP。
- broker 首版只接有有效安装记录和消费者绑定的本地插件 stdio MCP；
  手工原始 MCP 本轮不接 broker，不按服务名临时补一个授权身份。
- 可选、声明式的宿主能力申请；安装声明本身不授予账户访问。
- 官方 Step 的已识别账户 profile；保留当前 BVR 的地区/Plan/API 明确配对规则。
- text、video、asr 的兼容迁移，以及经实际能力验证后的非流式 tts。
- 原有插件详情、通用配置、原生授权和安装更新流程，不加载任意插件前端。

暂不包含：

- 把宿主 Key、Cookie、OAuth access/refresh token 交给插件。
- 携带宿主凭据的任意 HTTP 代理、作者指定 URL/请求头、跨渠道自动回退。
- 远程 MCP、外部任意进程或独立第三方应用直接接入本地 broker。
- 任意提供商认证、远程 OAuth 流程、无人值守持久授权、后台定时任务首次授权。
- 流式语音、云端音色复刻/上传/删除、任意文件读取和远程 URL 下载。
- 图像生成、图像编辑或 StepImage 插件实现；仅在第 5.6 节说明后续扩展方式。
- 自动执行 npm/pip/install/postinstall；通用 Python/原生二进制环境安装器。

通用指作者和插件身份可扩展，不代表任意 URL、任意模型或任意 API 都被授权。

## 4. 作者面对的契约

### 4.1 分清四份声明

| 文件 | 职责 |
| --- | --- |
| `step.plugin.json` | 原生身份、资源、MCP 启动声明 |
| `dfsc.plugin.json` | 展示、作者、文档、分类、外链 |
| `dfsc.settings.json` | 既有声明式独立配置，继续使用 `json-file-v1` |
| `dfsc.host.json`，拟新增 | 可选的宿主模型能力申请，不包含账户或授权结果 |

拟议的最小宿主能力声明：

```json
{
  "schemaVersion": 1,
  "hostApiVersion": 1,
  "consumer": { "kind": "mcp-stdio", "server": "stepaudio" },
  "capabilities": ["model.tts"]
}
```

此形状须在 [Ⅱ] 冻结并附 JSON Schema、主进程校验和有效/无效样例。
服务名必须绑定本包原生 MCP 声明，不可指向其他插件或原始 MCP 配置中的同名服务。
首版每包至多绑定一个 stdio 消费服务；有界的扩展需求另升协议版本。
未知能力不授予，未知主版本禁用跟随模式并给出兼容提示；其余独立资源按原规则运行。
声明文件、消费者代码、SDK bundle 和许可证均纳入市场同步与内容锁。

`dfsc.host.json` 不能自行指定已授权、账户、渠道、全局 token 或请求目标地址。
若上游已有可安全复用的等价声明，先比较再冻结；不能同时维护两套等价申请机制。

### 4.2 跟随模式和独立模式分开

- 声明能力后，插件详情才显示宿主维护的“使用 DFSC 账户”入口。
- 显式启用跟随模式仅保存用户选择，不等于已授权付费请求。
- 模型/渠道选项由宿主提供；聊天跟随实际调用会话，ASR/TTS 使用专用模型选择，
  不把当前聊天模型字符串拿去充当语音模型。
- 独立模式继续走通用配置表单，由插件读取它自己的地址、Key 和模型。
- 首版两种模式互斥。跟随失败不自动读取独立 Key，也不进行 Plan → API 切换。
- 所有配置、生成音频、缓存和运行状态放在安装包目录外，避免破坏包指纹和更新。
  宿主分配的配置/数据定位属于运行时绑定，不接受作者自报任意 profile 路径。

作者只实现业务函数、标准配置消费者和通用 host client，不增加按插件 ID 分支的宿主表单。
手工原始 MCP 首版只获得默认凭据隔离，不提供 broker 接入入口。
用户可将其封装成符合已安装插件契约的包，另行安装和申请；
本轮不设计原始命令、外部代码与任意远程服务的独立登记授权系统。

### 4.3 权威模式、配置和包外数据

在 [Ⅱ] 冻结生成的 `dfsc-launch-v1` 启动上下文，不新增一份作者手填清单：

- 宿主在私有存储持久化唯一的连接模式绑定，至少包含安装实例、消费者、
  包/host 声明指纹、模式、host revision、已应用模型选择和配置修订引用。
  模式不是作者环境变量、插件默认值或独立配置表单中的第二份开关。
- 宿主经受信启动通道提供有界、不可变的启动上下文；标准 client 验证归属后读取。
  上下文包含 `mode`、安装/消费者身份、修订引用和本实例包外数据目录，
  仅在跟随模式含 broker 连接信息，不含提供商凭据或独立配置秘密。
  具体定位和完整性校验在 [Ⅱ] 与 client/fixture 一同冻结，不让插件猜 profile 布局。
- 标准消费者先读取启动上下文，再按模式分支。独立模式才调用既有
  `json-file-v1` 读取器并验证必填 Key 等字段；不修改该协议对已提交配置的原有校验。
  跟随模式不要求存在独立配置 binding、独立 Key 或已保存的独立配置。
- 只申请宿主能力、没有 `dfsc.settings.json` 的插件，也能在用户选择跟随后启动。
  不靠保存空 Key 或伪造配置成功来绕过独立配置校验。
- 切到独立模式前先验证所引用的独立配置已成功提交，再原子提交模式指针。
  切到跟随模式仅提交 host 选择；任一步失败都不能静默改变有效模式。
  模式切换、独立配置变更和 host 模型变化均生成新 revision，撤销旧启动上下文；
  staging、指针提交、中断恢复和并发保存的顺序必须通过定向测试后才能冻结契约。
- 实例数据目录由宿主在 `step-runtime/desktop-plugins/data/<instance>/` 创建并校验，
  不在已安装包内。标准 client 返回这一权威目录供作者保存音频/缓存；
  locator 不是文件系统沙箱，也不向 renderer 提供任意文件访问。
- 同源更新保留安装实例和数据；卸载撤销调用权限但默认保留数据，
  另行确认后才清理。重装产生新实例，不自动认领旧秘密或旧数据。

必须测试“从未填写独立 Key → 选择跟随 → 握手 → 等待首次付费确认”，
以及“跟随被拒绝不切独立”“切独立缺 Key 不提交模式”“切换中断不混用旧配置”。

### 4.4 自包含交付路线

新增一个真实使用官方 MCP SDK 的 Node 示例：

1. 开发仓库含源码、固定 lockfile、构建脚本、测试和第三方许可说明。
2. 作者在自己的构建环境生成自包含入口和必要数据文件，Node 内置模块不打进 bundle。
3. 投稿快照包含固定提交中被跟踪的发布物，不提交 `node_modules` 或真实私密文件。
4. 市场用窄范围忽略例外允许发布物；测试 `dist/` 的跟踪、同步、哈希和实际加载，
   不能只改目录名来回避依赖问题。
5. 当前市场单文件 8 MiB、总计 32 MiB、1000 文件的限制继续生效。
   超限、动态 require、原生扩展或独立进程不在“单文件打包即可”的承诺内。
6. 首版示例明确需要本机可用的受测 Node.js 版本，并做启动前检查。
   不因 DFSC 内部携带 Node 就承诺第三方插件已自动使用该 Node；
   通用宿主 Node 启动别名另行设计，不在本计划顺带改变所有命令解析。

市场和作者构建可以运行经审核的测试；用户安装阶段不运行作者构建脚本。
固定 lockfile 与构建日志是可复核依据，不等于已证明跨平台字节级可重现。

## 5. 通用宿主模型 broker

### 5.1 结构

```text
插件业务代码 + 官方 MCP SDK + 通用 host client
                 |
          每次启动独立的本地调用凭据
                 |
Desktop Plugin Model Broker
  安装/来源绑定 -> 能力校验 -> 原生确认 -> 官方 provider adapter
                 |
             Step 模型服务
```

broker 由 Electron 主进程持有真实账户、请求目标和授权账本。
原生 MCP 启动适配只负责验证消费者、注册子进程启动实例并注入短期连接信息。
不把 broker 注册权限暴露成插件可调用的 IPC 或 MCP 工具。
renderer 只收到公开状态和授权视图，不能读私密文件或执行第三方 JS。

### 5.2 身份和连接

- 为每个安装实例、消费者和本次启动生成独立随机调用凭据，不复用 BVR 全局 token。
- 绑定至少包含：安装实例、来源身份、包指纹、能力声明 hash、配置 revision、
  宿主 runtime 实例、实际会话、MCP 启动实例和账户选择 revision。
- 凭据只经受信启动通道注入目标进程；不写入插件包、README、工具结果或全局 `host.json`。
  保留名由宿主控制，作者环境变量不能覆盖或重新指定 broker。
- 客户端自报的 PID、插件 ID、会话 ID、模型或来源均不作为授权依据。
  所属关系来自宿主的真实启动记录，不以“猜中一个活跃 PID”认证。
- HTTP token 是 bearer capability：注册记录约束它所能代表的身份和权限，
  不证明此刻提交 HTTP 的进程身份。若 token 被故意转交或窃取，持有者可能冒用原租约；
  首版保证的是未泄露凭据下的租约隔离，不声称复制 bearer 后仍能识别提交进程。
  若未来要求不可转移的进程身份校验，需要另选可核验对端的 IPC，而不是继续叠加 PID 字段。
- 标准 client 启动时取走并从进程环境删除连接密钥，默认不让普通业务后代继承。
  多进程插件应由已登记的 MCP 消费者保留 client，并以自己的业务 IPC 转交结果；
  不新增任意后代注册或共享 host token 机制。不承诺限制恶意插件主动复制自己的凭据。
- 首版使用仅绑定 `127.0.0.1` 的窄接口，拒绝浏览器 Origin、错误 Host、
  非预期方法/路由、重定向和无效 token；不提供 CORS 或浏览器访问。
- 进程退出、会话结束、应用重启、配置/包/账户变化立即撤销；凭据还应有有界有效期。
  长任务如需续期，必须通过同一受信启动绑定重核，不能由旧 token 无限续租。
- 同一 OS 用户的恶意原生程序仍可能读取其他用户文件或进程信息。
  这里防止的是错误注入、串插件和越权使用，不宣传恶意代码沙箱。

### 5.3 能力接口

冻结窄的 `context`、`invoke`、`cancel` 契约，不开放原始 fetch：

| 能力 | 模型和输入 | 返回 |
| --- | --- | --- |
| `model.text` | 当前会话模型；有界消息和选定参数 | 规范化文本 |
| `model.video` | 通过宿主能力核验的会话模型；有界内联视频 | 规范化文本 |
| `model.asr` | 同账户、地区和渠道的受支持 ASR 模型；有界音频 | 规范化转写 |
| `model.tts` | 宿主允许并由用户选定的专用 TTS 模型；文本、音色、格式 | 有界音频字节与 MIME |

`context` 返回协议版本、可用能力及原因、已应用选择和不透明 revision，
不返回上游地址、Key 或 Cookie；查询本身不触发模型请求。
`invoke` 必须携带本次 context revision；过期时拒绝，不自动切到新账户重试。
`cancel` 仅能取消同一启动身份的请求；断连也撤销对应活动请求。
取消无法保证已经被服务商接受的任务不计费，界面和协议都明确说明。

首版候选限制在 [Ⅱ] 冻结：文本响应 2 MiB，媒体请求 JSON 32 MiB，
TTS 解码音频 16 MiB / 响应 JSON 24 MiB，每插件每会话并发 2，
全局模型并发 8，provider 请求截止时间不超过 180 秒。
原生确认有独立超时，未经确认不占用 provider 请求；排队和请求都有有界总期限。
这些是资源限制，不是精确费用估算或硬金额预算。
超限显式失败，不靠截断、换模型或额外重试生成第二笔请求。

TTS 首版只接经过核验的非流式字节响应，不让宿主接受任意输出文件路径。
作者负责将音频保存到自己的包外数据目录。URL-only、未知 MIME 和超大结果明确拒绝；
不借“取音频”开放任意 URL 下载。云端音色查询、上传与复刻另设能力，不混进 `model.tts`。

### 5.4 授权和撤销

安装、审核入库、启用服务、选择跟随模式和 Full Access 均不等于付费授权。
首次付费调用必须由宿主弹出确认，展示插件、来源、具体能力、
实际模型、账户地区、Plan/API 渠道、发送的数据类型和额度/费用影响。

首版只做本次会话内授权；授权键包含安装实例、包指纹、消费者、
能力集合和已应用账户/模型选择。进程重启或包更新后重核，不从旧名称推导授权。
插件详情可查看当前允许的能力、撤销和待重启状态，不新增独立授权中心页面。
后台/Cron 没有可交互确认时返回“需要用户授权”，不替用户点击或假定已有许可。

同一授权范围内并发申请合并为一次确认；拒绝不循环弹窗。
申请超出已同意能力、切账户/地区/渠道、换专用语音模型或扩大声明，必须重新确认。
确认返回后、实际发送前和结果返回前都检查 revision；
等待确认期间切会话、更新或撤销，不能继续使用旧授权。
撤销立即中止待执行请求并拒绝新调用；已经被提供商接受的请求可能仍计费。

### 5.5 Provider adapter

不把 BVR 的私有协议直接改名成通用协议。
复用它已经验证的官方 profile 映射、原生确认、revision 和无回退规则，
按能力分离 endpoint、模型校验、参数和输出解析。
首版保留官方、可识别、未过期的 Step 账户边界；其他账号/自定义渠道返回明确不支持。

tts 的地区、渠道、模型、返回格式必须形成有证据的支持矩阵。
未知不等于支持，也不等于官方不支持；不以“用户能聊天”推导“该账户能 TTS”。
外部文档、本地 mock、真实账户成功和真实计费观察分开记录。
未完成某组合的验收，UI 不显示已就绪，SDK 返回原因而不降级直调。

### 5.6 后续能力扩展：以 StepImage 为例

通用层复用安装身份、启动租约、账户选择、授权、撤销和错误协议，
不把提供商目前有哪些模型写死为按插件区分的分支。
假设未来官方 Step Plan 对相应地区和账户开放图像接口，可按以下方式扩展：

1. 宿主新增一次通用 `model.image` adapter，核验实际接口、模型、
   地区/渠道、输入输出和资源上限，并登记最低宿主能力版本。
   这是新的能力适配工作，不是填一个模型名称就自动获得支持。
2. StepImage 等插件声明申请 `model.image`，通过同一 host client 查询和调用；
   宿主已经支持该能力时，后续作者不需要再提交专属 DFSC 代码。
3. OAuth 登录只证明账户身份，不证明图像接口权益。实际可用性仍按账户、
   地区、渠道和模型核验，不因能调用文本或 TTS 就推定可调用图像。
4. 图像是独立授权能力；已有 text/TTS 同意不能覆盖它。
   插件更新扩大能力声明后须重新确认，不能沿用旧授权增加调用权限。
5. 不支持该能力的旧宿主返回明确的能力/版本原因，不回退到插件独立 Key，
   不改用 API 计费，不经通用 broker 开放任意 HTTP、文件或 URL。
6. 新媒体形态的输入、输出、取消、超时、体积限制和隐私测试随 adapter 冻结；
   不能仅沿用文本返回格式，就宣称图像接入已完成。

若未来接口只需要新增已支持能力内的模型，仍须核验并更新能力矩阵；
若是新的 API 形态，则由宿主补通用 adapter，所有申请者复用。
本例不声称当前 Step Plan 已开放图像能力，也不加入本计划首版实施与完成门槛。

## 6. 实施顺序与独立验收门槛

### [Ⅰ] 凭据默认隔离与风险披露

- 在 Desktop 的固定 pin 适配补丁中关闭第三方 MCP 的 Step 登录自动注入。
  不升级 pin、不直接改用户维护的 Step-Code checkout。
- 显式配置的插件独立 Key 仍按既有私密配置规则消费；
  不用“清空所有秘密环境变量”破坏用户有意配置的独立服务。
- 清点插件 MCP、手工 MCP、嵌套子进程和内置 MCP 的启动路径；
  宿主内置服务如需要账户，使用明确维护的 adapter，不能只凭自报名绕过策略。
- 已依赖隐式注入的旧服务提示重新配置/授权，不静默恢复注入或直接改用户配置。
  已运行的旧进程只有在显式重启后才能获得新隔离，不能宣称已收回其已收到的 Key。
- 此阶段先在隔离候选中落地，不单独发布一个缺少后续迁移入口的破坏性升级；
  完整发布须满足 [Ⅲ][Ⅳ] 的 BVR 退场和可操作兼容提示门槛。
- 安装说明和首次安装确认披露第三方代码、网络/文件能力及真实计费风险，
  区分来源锁定和安全保证；兼顾 UI 语言，不复制长篇法律免责。

门槛：假 OAuth/API Key 均不进入第三方进程、后代、日志、renderer 或工具结果；
独立 Key 的显式消费不回归；BVR、内置服务和原始 MCP 的兼容结果逐项记录。
在 broker 完成前，受影响服务可以明确不可用，不以泄露凭据换取“无感兼容”。

### [Ⅱ] 作者契约、声明与 SDK 打包样例

- 社区 README/CONTRIBUTING 增加单一作者入口，链接版本化指南和真实示例。
- 发布原生 MCP 启动字段的完整支持子集、占位符的旧兼容含义、
  设置 schema、拟新增 host schema、更新规则和宿主能力版本表。
- 文档与校验器共用有效/无效样例，明确结构校验、运行时校验和原生验收的区别。
- 冻结第 4.3 节启动上下文、唯一模式来源、数据目录、提交/恢复顺序和版本协商；
  先以没有任何独立 Key 的消费者走通跟随路径，不把此问题留到 UI 完成后才处理。
- 更新市场卸载重装旧说明，解释“更新市场”与“更新已安装插件”。
- 实际演练 SDK 安装、作者构建、固定提交同步、无 node_modules 的全新安装。
- 不复制 BVR 私密配置 CLI 作为普通作者的默认教程。

门槛：没有宿主源码背景的审查者只读市场入口，能指出需提交的文件、
依赖交付方式、模型调用申请、配置和更新方法；全新目录能通过上述流程。
此阶段的 host 声明和 client 只标为草案，不冒充旧宿主已经支持。

### [Ⅲ] broker、配置入口和受信启动绑定

- 在 [Ⅰ][Ⅱ] 基础上实现通用 broker、typed preload、主进程权限状态及窄 RPC。
- 复用安装 receipt、包指纹、配置 revision 和现有服务开关生命周期。
  来源未知、身份冲突、外部改动、失败安装和含糊 transport 覆盖均拒绝账户绑定。
- 在详情“配置”增加宿主维护的跟随入口；复用现有控件、页签、
  `CapabilityDisclosure`、焦点边框、三次方动效和 reduced motion。
- 编写通用 host client 和 mock broker fixture，作者无需知道宿主文件布局或 BVR token。

门槛：两个不同来源/安装实例的插件并发运行不能串授权；
客户端伪造 ID/PID、使用 A 的 token 申请 B 的身份/能力、过期租约、Origin/Host 攻击均失败。
复制仍有效的 A token 并完全冒用 A 不列为“必拒绝”断言，按第 5.2 节 bearer 风险说明；
另测标准 client 移除环境连接密钥、普通后代不意外继承。
手工原始 MCP 没有 broker token 或跟随入口，但仍覆盖凭据隔离回归。
各路径在原生 Step runtime 与 Electron 中测试，不以单测替代真实启动绑定。

### [Ⅳ] BVR 兼容迁移与 StepAudio 普通作者验收

- 先让 BVR launcher/消费者接入同一套受信启动绑定，再委托 broker 权限和 provider 内核。
  仅共享 provider 内核、不改入口身份认证不算完成迁移。
- 发布门槛：关闭接受旧全局 `host.json` token 和自报 runtime PID 的入口，
  不再生成该全局连接凭据。旧路由若短暂保留，也必须使用新的消费者启动租约，
  不接受旧 bearer；清理本应用所属的临时 descriptor，不改独立 Key 或用户业务配置。
- 最低 BVR launcher 以已验证的 host API v1 协议标识及明确发行版本/固定提交登记，
  具体版本和 SHA 在实施 PR 中填写并经适配测试核对，不能凭自报标识授予权限。
  发布前没有这一兼容记录则阻止发布；旧 launcher 明确提示升级，跟随暂不可用，
  用户可显式选择独立模式，不静默兼容旧鉴权。已运行旧应用需用户重启才会退出旧桥。
- BVR 原有独立配置不自动变成跟随；旧同意记录不自动变成通用能力授权。
  text/video/asr、账户切换和拒绝后的行为均不回归。
- 另在作者仓库以独立变更接 StepAudio：官方 MCP SDK bundle、
  `dfsc.settings.json`、host client、包外音频目录和清楚的模式说明。
- StepAudio 跟随模式首版只开放经核验的 TTS；离线音色目录可用，
  未纳入的云端音色/复刻操作明确不支持，不偷偷用独立 Key。
- 包更新先撤销旧启动的 host 权限，再按新指纹重核。
  能力扩大必须重新确认；更新失败/回滚不能保留跨版本旧 token。
  独立 Key、配置快照和数据不因普通同源更新丢失。

门槛：同一 DFSC 二进制，仅更换/安装两个插件包即可接入，
没有 `if plugin.id === "stepaudio"` 的授权或表单分支。
离线 mock 先验证完整数据通路；真实账号调用需另获用户授权，
按地区/渠道分别记录能力和计费观察，不宣称全组合已验证。

### [Ⅴ] 跨仓库收尾与可发现性验收

- 宿主仓库：broker、启动适配补丁、schema、client 示例、UI 和回归。
- 社区市场：依赖政策、风险说明、作者入口、声明/产物校验和新的锁定资源。
- BVR/StepAudio：各自客户端、消费者、发布物、许可证和随包说明。
- 先使宿主契约可用，再合作者发布物和市场收录，最后确认正式客户端可发现。
  对旧宿主明确显示需要的能力版本，不能仅用相同 `0.6.0` 号推断兼容。

本次授权只覆盖计划文档的提交和 PR。后续实现、跨仓库提交与 PR、公开投稿、
真实付费调用和 Windows/macOS 打包仍须另行授权。

## 8. 完成定义

- 普通作者无需查看 BVR 私有实现即可完成配置、构建和提交。
- 官方 MCP SDK 能被真实打包、安装、加载；用户不执行依赖安装脚本。
- 插件不能通过默认启动环境获得宿主提供商凭据。
- 授权按实际安装与调用身份隔离，跟随模式不泄露 Key、不自动切计费渠道。
- BVR 与 StepAudio 复用同一 broker，普通接入不要求再编译一个专配 DFSC。
- 配置、数据、权限和更新生命周期相互区分，并有负向及恢复测试。
- 文档、schema、校验器、宿主能力版本和市场说明一致。
- 未支持的提供商、运行环境和 API 能明确报错，不靠猜测或假按钮表现支持。

“同一系统用户的恶意程序无法读取任何秘密”不属于完成定义；
若要对不可信原生代码建立真正文件/进程沙箱，应独立立项。
