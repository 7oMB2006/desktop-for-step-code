## 调用链

```text
首发 createDraftSession
  -> connect
  -> SessionRuntimes.openWorker
  -> initializeModel
  -> pluginsReady / PluginHostLauncher.attach
  -> CapabilityService.withHostDescriptor
  -> 原 readCatalog
     -> 管理进程扫描已安装插件和全部市场候选、计算完整包指纹
     -> 主进程投影展示元数据、主题安全性和更新状态
     -> library.reference 再次校验多个插件、市场候选的完整指纹
  -> 会话创建返回
  -> 首条 prompt
```

宿主只需要证明目标已安装消费者的身份和授权前置条件，却等待了与执行无关的
整个插件中心展示和更新目录。安装较大的插件会放大这一依赖，影响其他模型的新会话，
而非只影响该插件自身或某个新供应商。

这里的启动是会话 worker 的建立、恢复或重启，不是整个软件仅首次启动时的一次检查。
已启用的 MCP 会自动参与运行时准备，因此 Bilibili 宿主会被核对；这不表示用户的
首条问题要求了该插件，也不表示模型已经调用业务工具。切回仍在线的 worker 不等于重新启动。

## 本地修复

- 增加仅管理进程可调用的只读 `host-descriptor` 操作，核对目标插件，不读取市场目录、
  不投影插件文档/主题/更新状态，不为无关插件重新计算完整指纹。
- 保留目标目录规范路径和链接检查、重复安装 ID 检查、安装凭证与完整包指纹、
  原生插件发现、stdio 声明、禁用状态、用户同名覆盖和未完成更新检查。
- 描述符解析及宿主发放仍在原 CapabilityService 串行事务内。未引入持久指纹缓存，
  未跳过 broker、账户、租约、模型或宿主消费者的再次验证。
- 模型恢复和插件附加分别记录为 `modelRestoreMs`、`pluginAttachMs`；
  插件阶段失败、关闭和迟到完成继续遵循原运行时身份及清理约束。
- 新管理操作采用 30 秒 RPC 预算；管理进程退出未确认时仍隔离服务，不继续发放宿主。

上述启动修复只涉及 Desktop 管理辅助程序、宿主描述符入口和启动计时，不改上游源码、
模型请求协议、正式凭据、插件内容或日常应用配置。

## 后续更正：r1 漏检与 r3 阶段性冷启动对照

本节更正前述 r1 的完成范围，不改写原始测量或把此前通过记录改称失败。
用户用 r1 打开正式 profile 后仍然很慢，证明“已完成隔离验收并交付 r1”
不等于“本次现场问题已经解决”。初轮窄宿主描述符修复有效，但没有移除另一条自动入口：

```text
主窗口挂载
  -> 为桌面插件菜单自动调用 capabilityCatalog()
  -> 整个插件中心的已安装包、市场副本、展示与更新目录扫描
  -> 占用 CapabilityService 的 FIFO 串行队列
新会话/历史恢复
  -> capabilityService.recover()
  -> 排在上述目录读取之后
  -> 然后才建立并计时 session runtime
```

因此即使 `withHostDescriptor` 已经只核对目标插件，仍可能先等自动完整目录查询。
用户不需要打开插件中心，也不需要明确要求加载插件，就会触发这段等待。
同一正式插件 profile 的独立只读诊断中，完整 catalog 为 **80.072 秒**
（当轮工具观测，输出未单独落盘，不虚构对应日志路径）；
本轮中间源码的窄桌面菜单读取为 **624 ms**，返回 2 个已安装入口、0 个市场候选，
源码主进程插桩的 `fingerprintScans` 为空。两者范围不同，只是单次本机观测，
不能称为 P95、完整冷启动或 r3 的正式用户场景验收。

初轮 `verify-session-plugin-startup.mjs` 在首问计时前先等待目录读取、保存宿主配置，
再做独立诊断，已经把昂贵队列排空；1200 文件夹具还是无关资源包，没有同规模市场副本。
所以其中约 3 秒首答和窄宿主指标不能证明“刚打开应用就立即首问”的响应性。
`runtimeStartupTiming` 从 session runtime 内部开始计时，覆盖不了前置管理队列等待；
模型恢复和插件附加分段正确，也不能据此排除 runtime 计时之外的阻塞。

后续修复将主窗口自动菜单改为 `pluginDesktopCatalog()` / `desktop-catalog`：

- 只读取安装凭证及有界的导航元数据、页面和图标，不枚举市场或递归依赖目录，
  不对全部插件计算包指纹。真正打开插件中心时仍使用原完整目录。
- 保留 FIFO 和事务边界。菜单引用只用于展示，不自动授予文档、执行或其他动作权限；
  目标文档和动作仍经完整目标包校验，不用安装时的指纹替代动作时的核验。
- 保留真实主窗口入口、刷新与过期结果保护，部分菜单投影不会删除完整目录已发出的引用。
  插件窗口不因此得到新菜单接口权限；没有关闭安全检查、加入永久指纹缓存或改供应商协议。

后续审查发现：可选 `desktopCatalog` 在 r3 中仍与会话恢复共用 FIFO。
因此慢菜单请求或管理进程停止失败的路径仍可能拖住会话；下述速度用例未复现这些路径，
不能据此证明故障隔离成立。r3 只保留为阶段性性能对照，不作为最终用户交付；
后续隔离修正和最终结果见 r5 节。

### 同规模冷启动对照

新增 `verify-session-plugin-cold-start.mjs`。SDK 独立配置在启动前通过真实配置 store

验收 harness 不先调用 catalog 或诊断。使用本机 loopback 模型，不复制真实凭据或执行正式插件。

| 包与操作 | 启动至首答 | 交互至首答 | runtime 总启动 | 插件附加 |
| --- | ---: | ---: | ---: | ---: |
| r1 确认对照：立即首问 | 85908 ms | 84287 ms | 2385.85 ms | 857.04 ms |
| r3 阶段对照：立即首问 | 5729 ms | 3557 ms | 2805.09 ms | 1052.22 ms |

表中“首答”指 bridge 快照中停止流且已含本轮响应，不证明 renderer 已完成首答 DOM

r1 约 81901 ms 的交互等待不在 runtime 启动指标内；不能将这个差值直接等同于
某个函数的精确耗时。旧包确认轮按原性能阈值失败，未调高阈值使其通过。
首轮旧包对照的性能失败也保留，但其全局退出错误曾被 harness 收尾访问已解绑

r3 两组均保留 SDK 与大包桌面入口；真实 SDK 每组只启动一次，连接后提供 2 个工具，
大包精确 MCP 服务为禁用且零启动。两个 Electron 均正常退出，loopback 服务关闭，
临时 profile 删除后再次验证不存在，renderer pageerrors 为零。
首问退出日志仍有一条异步 IPC `This session runtime is not connected`，
不能把进程正常退出和页面无异常写成“全部日志干净”。

计时从 `electron.launch` 调用开始，fixture 写盘与预配置约 19--21 秒单列且不计入用户启动；
app-ready、窗口与可操作时间是自动化观测上界，不是插桩的原始 ready 事件。
只测试应用冷进程，未控制操作系统文件缓存，也未插桩 renderer 自动调用的动态次数。
历史 case 是小型合成历史，不覆盖正式 profile 的百余 MB 历史和大文件恢复。

不是每项单独冷进程，未控制 OS 文件缓存，也未插桩 renderer 自动调用次数。

### 修复与安全边界

新增 `target-catalog` 仅核对目标的目录、安装实例、凭证、来源和消费者身份；
MCP 碰撞检查仍读取全局声明，但不递归校验无关包内容。菜单引用只负责定位，
不会自行获得文件权限。目标操作在首尾完整指纹之间使用一次性读作用域，
读操作退出前再核对目标身份；作用域不能伪造、跨描述符转移或在下一次操作复用。
未引入持久指纹缓存，没有跳过链接检查、更新屏障、秘密投影或消费者冲突检查。

业务校验失败也必须完成末次包校验。包变化、目录消失或被替换时，末次错误可以覆盖
原业务错误，同时撤销旧引用；恢复原字节不会恢复旧引用。正常业务错误且包未变时，
不误撤销有效引用。保存成功返回后不再创建管理 worker，以免提交后的附加管理请求
产生新的不确定状态；末次指纹失败报告 `settings-committed-unverified` 并撤销引用，
重新获取引用后读取已保存版本，不提示用户把已提交的设置当作完全未保存。
这不意味着 store 自身未成功返回时也能确定提交结果，原有不确定及
`host-selection-incomplete` 边界仍保留。

r6 API 单步已低于门槛，真实配置页却仍用了 24365 ms。原因是 `openPlugins()`
激活插件中心后读取 settings，新对象引用触发再次完整 catalog，排在宿主设置前面。
r7 改为观察真实 MCP 设置内容，规范名称和秘密字段名顺序、保留启动参数顺序；
首次 settings hydration、等价新对象不再重复读，隐藏时不读，激活及实际变更串行刷新。
保留关闭重开、桥替换、在途变化和失败重试，没有调高性能门槛。
