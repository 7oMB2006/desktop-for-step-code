# 版本编号

应用版本使用 SemVer 三段格式。Windows 和 macOS 共用一套应用版本，不要求同步发布。

## 产品约定

- `0.x.0`：开发阶段的一批新功能，代表阶段性功能合集。
- `0.x.y`：相应功能版的修复和范围明确的小幅增强，例如 `0.5.1` 的套餐额度与 API 余额查询；不要求每次新增独立能力都推进功能版本。
- `1.0.0`：核心体验、数据兼容和升级路径经过验收，维护者决定开始承担长期维护承诺。
- `1.x.0`：兼容已有配置和数据的新能力。一个独立的小功能也可以单独发布，不必攒成大型更新。
- `1.x.y`：兼容性修复。
- `2.0.0` 等主版本升级：不兼容的产品契约变更。视觉改版、重构或 runtime 升级本身不自动要求升主版本。

发布次数不是主版本号；第二次 Release 不等于 `2.0.0`。功能版本可以继续增长到 `0.10.0`，不因为进位强行进入 `1.0.0`。

发布累积已经进入发布基线的改动。发布说明按各平台上一公开正式版比较；此前只向另一平台交付的能力，用平台标注说明本次首次提供，不当作所有用户都没见过的新功能。补丁继续递增第三段，不使用 `1.0.1.1`；实验版本使用 `1.1.0-beta.1` 等后缀。

## 平台与版本

- 各平台可以跳版。例如 Windows 发布 `1.0.1`、`1.0.2`、`1.0.3`、`1.1.0`，macOS 只发布 `1.0.2` 和 `1.1.0`；macOS 的 `1.1.0` 从该平台的 `1.0.2` 验证覆盖升级，不需要补装中间版本。
- 同一版本只用一个 Git tag 和一份 GitHub Release。各平台安装包都从该 tag 指向的同一个 Desktop 提交、同一个 Step Code 源码钉点及集成补丁构建。后发平台如需修改源码或运行时，跳过该版并为修复分配新版本。
- Windows 通常先发是排期默认，不是版本限制。macOS 不必逐版跟进，也不必为独立紧急修复等 Windows；实际可用的发版路径与限制见[发布与验收](RELEASE.md)。

## 候选流程

```text
0.2.0-beta.1 → 0.2.0-beta.2 → 0.2.0-rc.1 → 0.2.0
```

Beta 用于功能体验；RC 用于高风险变更的发布前验收。低风险发布可以直接构建并验收正式版本号的包，不要求先打 RC。RC 发现需要修改产品代码的问题，应使用下一候选编号。RC 通过后，将应用版本改为不带后缀的目标版本，重新构建并核验，不直接重命名 RC 安装包。

应用 `Desktop/package.json`、Git tag `v<version>`、Release 和安装器版本必须一致。`pnpm-lock.yaml` 不记录本项目自身版本，升版不需要无关依赖更新。

未公开的本地重建可以保持版本号，但应记录源码基线、安装器 SHA-256 和候选序号。公开后不移动 tag、不覆盖已公开的平台附件；允许同版后发的平台追加自己的附件，不能用追加代替升版修复。构建元数据 `+...` 不参与版本优先级比较，不能用来触发新版提示。

## 发布通道

SemVer 的先行版本后缀与 GitHub 的 Pre-release 标记是两个不同概念：

- Beta / RC 的公开 Release 必须标为 Pre-release。
- 早期社区预览允许将不带后缀的版本（例如 `0.2.0`）标为 GitHub Pre-release；`v1.0.0` 是正式 Release。
- 正式版通道排除 GitHub Pre-release 和带先行版本后缀的版本。
- 默认包含预览的通道允许二者，仍按 SemVer 比较。

正式 Windows x64 和 macOS Apple Silicon 安装版可在符合条件时由用户主动下载更新并确认重启安装；不自动下载，也不在普通退出时自动安装。不带更新器、不能原位安装或缺少更新元数据时使用手动下载。平台及旧版本差别见[更新说明](UPDATES.md)。
