# 版本编号

应用版本使用 SemVer，格式为 `主版本.功能版本.修复版本`。

## 产品约定

- `0.x.0`：开发阶段的一批新功能。
- `0.x.y`：相应功能版的修复，不引入新的主要能力。
- `1.0.0`：核心体验、数据兼容和升级路径经过验收，维护者决定开始承担长期维护承诺。
- `1.x.0`：兼容已有配置和数据的新能力。
- `1.x.y`：兼容性修复。
- `2.0.0` 等主版本升级：不兼容的产品契约变更。视觉改版、重构或 runtime 升级本身不自动要求升主版本。

发布次数不是主版本号；第二次 Release 不等于 `2.0.0`。功能版本可以继续增长到 `0.10.0`，不因为进位强行进入 `1.0.0`。

## 候选流程

```text
0.2.0-beta.1 → 0.2.0-beta.2 → 0.2.0-rc.1 → 0.2.0
```

Beta 用于功能体验；RC 用于发布前验收。候选发现需要修改产品代码的问题，应使用下一候选编号，不能把不同公开安装器放到同一版本下。RC 通过后，将应用版本改为不带后缀的目标版本，重新构建并核验，不直接重命名 RC 安装包。

应用 `Desktop/package.json`、Git tag `v<version>`、Release 和安装器版本必须一致。`pnpm-lock.yaml` 不记录本项目自身版本，升版不需要无关依赖更新。

未公开的本地重建可以保持版本号，但应记录源码基线、安装器 SHA-256 和候选序号。已经公开的版本内容不可替换；修复后发行新版本。构建元数据 `+...` 不参与版本优先级比较，不能用来触发新版提示。

## 发布通道

SemVer 的先行版本后缀与 GitHub 的 Pre-release 标记是两个不同概念：

- Beta / RC 的公开 Release 必须标为 Pre-release。
- 当前项目处于社区预览阶段，无后缀的 `0.2.0` 也可以标为 GitHub Pre-release。
- 正式版通道排除 GitHub Pre-release 和带先行版本后缀的版本。
- 默认包含预览的通道允许二者，仍按 SemVer 比较。

公开 `v0.1.0` 没有新版检查能力，用户首次升级仍需手动下载。本轮引入的更新机制只提示并提供系统浏览器下载入口，不自动安装。
