# v0.6.0 联合发布交接

Windows 和 macOS 并行准备，共用一个 GitHub Pre-release 草稿。维护者返回后先做 Windows 云测，再结合 Mac 原生验证进行交叉复查和二审；所有关键门槛通过后另行确认发布。**保持草稿，不点击 Publish，不自动合并 PR。**

## 共同基线

- 产品功能 main：`324e71d1800de020c035cdce598374a6037ba4ca`，包含 #160–#163。
- 版本准备分支：`codex/release-v0.6.0-preparation`，应用版本 `0.6.0`。两端应从同一干净、已推送的准备提交构建，记录完整 commit；不使用各自未提交的本地改动替换联合候选。
- 该分支的云测候选不等于最终 main/tag。准备 PR 合并后冻结最终目标；如源码、runtime 或应用构建内容变化，重新构建、生成校验值并完成必要回归，不能仅重命名旧包或覆盖相同的公开版本。
- 目标 tag 为 `v0.6.0`，准备阶段不创建 tag。草稿的 `target_commitish` 必须指向记录的候选提交；最终发布前再次核对。
- Windows runtime：`b5dbed938d9ae589397cf522dcf2ff89ecf4c494`，Node `v24.16.0`，使用同一提交的 `patches/v015/manifest.json`。
- macOS runtime：继续固定 `3ba89e0cbfe6be78cccdafb5aeafd2592177cbb8` 与现有 Mac 补丁；不得为了共用版本号静默升级钉点。Node、bundle 和 patched sources 以实际原生构建证据为准。

## Mac 侧接入

当前 Windows 连接中没有可访问的另一台 Mac 主机或已识别的 Mac 线程；本文件是共享交接契约，不表示已经启动 Mac 构建。

1. 获取共同准备分支，核对干净状态、应用版本和完整 commit。任何必须的 Mac 修复单独提交并回传，避免两端交叉改写候选身份。
2. 按 [MACOS.md](../MACOS.md) 在 Apple Silicon Mac 原生构建和验证。统一版本必须显式使用 `DESKTOP_MACOS_RELEASE_VERSION=0.6.0`，不能沿用默认的 `0.6.0-macos.1`。
3. 运行 `verify-macos-package.mjs`、`verify-macos-updater.mjs` 和适用的源码／包内回归。记录实际 macOS 版本、架构、Node、源码身份和 runtime manifest；CI 不能代替真实安装与账号验收。
4. 重点核对新 UI 与旧 runtime 的兼容：Usage 扫描、插件／MCP／Skills、Cron 基础管理及恢复增强、会话导入、CLM 修订查询、自动续跑来源。区分可用、明确不可用和未验收，不能把 Windows-only patch 的能力列为 Mac 已支持。
5. 记录窗口／菜单／快捷键、zsh、文件打开、终端 PTY、浏览器与变更面板的原生差异。缺少 capability 时必须清楚呈现不可用，不用模拟结果或 Windows 回归代替。
6. 在一次性测试用户或可恢复环境验证 `v0.5.1-macos.1 → v0.6.0` 的手动覆盖和适用的内置更新路径，确认资料保留。Developer ID 签名、公证和 Gatekeeper 限制以实际结果披露，不移除隔离属性绕过系统检查。
7. 从同一干净提交运行 `prepare-macos-release.mjs`，生成 ARM64 ZIP、`mac-update.json`、平台校验值、`COMMIT.txt` 与 runtime manifest。完成检查后接入同一个 Release 草稿，不发布。

Mac 可以先并行准备依赖和验证环境；若共同提交尚未推送，不自行从另一个未经确认的 HEAD 出最终附件。

| 构建与验收记录 | 双方 | 完整源码提交、是否干净、runtime pin、Node、哈希、检查结论和例外，不含凭据或个人会话。 |

上传前查询草稿是否已存在，沿用其 ID；不另建同名 Release、不替换另一端附件。仅在明确核对新旧内容且尚未发布时替换自己的候选附件，并同步自己的更新元数据及合并校验清单。公开后不得替换二进制。

平台构建脚本生成的同名 `COMMIT.txt`、`runtime-manifest.json` 如需上传，先合并为明确区分平台的证据文件，不能互相覆盖；runtime manifest 不应重命名后被错误当成更新元数据。

## 草稿与发布操作

- 草稿创建时 Windows 正文仍是 Windows 能力说明；Mac 侧需追加平台范围、不可用能力和安装说明，二审前不能当作联合最终正文。
- 只保存 GitHub draft，`draft=true`、`prerelease=true`。不设置公开 Latest，不提前刷新生产更新清单，不将 `0.6.0` 写成已经公开。
- Windows 云测后填入真实账户、安装／覆盖升级／重启等结论；只核销实际确认的用例。
- Windows 侧复查 Mac 的源码身份、附件元数据、校验值和差异说明；Mac 侧二审 Windows 的相同证据及联合正文。
- 双方确认最终 tag 目标、版本、附件集合、风险披露与检查结果，维护者明确批准后才发布。
- 发布后分别验证 Windows 与 `platforms.darwin` 更新清单，公开下载回验哈希；不把一个平台的成功当成另一个平台通过。
